S84 Specialization across abstraction boundaries #

An operating system can offer the same operations to many applications while fixing choices that matter differently to each of them. A file-copying program, a web server and a database can use familiar interfaces yet benefit from different arrangements of memory, storage and communication. The architectures examined here change which choices an application can make, which implementations it can replace and how those choices are protected. Their histories include both exposing lower-level resources and retaining interfaces while changing the work performed behind them.

Moving management into a replaceable library#

Dawson Engler, Frans Kaashoek and James O’Toole’s 1995 exokernel design separates protection of resources from their management. A small privileged kernel tracks ownership and controls access to physical resources. Library operating systems implement higher-level abstractions, such as virtual memory, interprocess communication and files. An application can use a library supplying familiar services or a specialized implementation suited to its task. Replacing a library need not require replacing the kernel. [XA-W001]

The authors identify several restrictions imposed by a fixed privileged implementation. A general replacement policy can be poorly matched to a database’s predictable access pattern. Hiding faults or timing information can obstruct an application’s own management. A new abstraction can require awkward emulation through an existing one. Their proposed change gives application software control of implementation decisions that would otherwise belong to the operating system. It extends the question of function placement developed in S12 to resource management. [XA-W001]

A secure binding separates authorization from subsequent use. When access is established, the system can examine the relevant ownership and permissions; later accesses can be checked through simpler hardware or software mechanisms. The kernel need not understand every higher-level purpose for which an authorized resource will be used. The design also exposes allocation and resource names so that an application can choose specific resources using information about their properties and availability. [XA-W001]

Control remains bounded by the kernel’s power to allocate and reclaim. Visible revocation lets a library choose which resource to surrender and adjust its own state. An abort protocol allows the kernel to reclaim resources when an application refuses to cooperate. Allocation denial and revocation can enforce quotas or other policies among competing applications. Moving management into a library therefore changes the application’s available decisions while preserving an authority that arbitrates access. [XA-W001]

Sharing disk data without prescribing one filesystem#

The later Xok/ExOS system makes protected sharing a concrete design problem. A library filesystem needs control of disk layout, caching and requests, but several libraries may access the same files. Partitioning the disk among applications would prevent useful sharing. XN, Xok’s storage substrate, instead protects blocks and metadata while allowing library filesystems to interpret and arrange them. [XA-W002]

Its buffer-cache registry records the association between a disk block and the physical page holding a cached copy. The data remain in application-managed pages. A library can inspect the registry to discover what is cached, but mapping a page requires corresponding access rights to the disk block. This arrangement permits reuse of cached data without giving every participant authority to modify it.

Libraries retain choices about replacement, prefetching and the division of their memory between cached files and other uses. [XA-W002]

Protection also concerns how metadata establishes ownership. XN uses deterministic metadata-interpreting functions to check whether a proposed update correctly tracks the blocks controlled by a filesystem object. It enforces ordering rules needed to prevent a crash from creating unauthorized access. For example, a persistent pointer must not expose uninitialized metadata, and a freed block must not be reused while old persistent pointers still refer to it. Libraries choose operations and schedules consistent with those rules. [XA-W002]

C-FFS supplies Unix filesystem behavior on this substrate, including access-control mappings and invariants such as unique names within a directory. ExOS supplies ordinary Unix abstractions through libraries. In the 1997 implementation, some shared tables were not yet fully protected; the ordinary-application experiments included extra calls to estimate the cost of checking writes to them. Those experiments showed comparable performance with conventional systems, including a 41-second workload total on ExOS/C-FFS against 51 seconds on OpenBSD/C-FFS. The specialized applications discussed next were measured without the newly developed XN substrate. [XA-W002]

Copying files without touching their contents#

XCP uses the exposed storage and cache interfaces to change how copying is scheduled. Given a list of files, it first enumerates and sorts their disk blocks. It can then issue large asynchronous reads in an order suited to disk access, rather than follow an application-level sequence of small reads and writes. Concurrent instances can have their disk schedules merged by the driver. [XA-W002]

While reads proceed, XCP creates destination files and allocates their blocks. As data arrive, it constructs large writes using the buffer-cache entries. The disk controller transfers data into and out of the cache through direct memory access; the CPU does not copy or examine the contents. Allocation, reading and writing overlap, and cached pages become the connection between the two sides of the copy. [XA-W002]

The authors report XCP running three times faster than cp using Unix interfaces on the same Xok/ExOS system. For resident files, avoiding CPU data movement contributes to the gain. For files on disk, large contiguous transfers and a schedule with fewer seeks also matter. The library filesystem makes it possible to combine operations around the copying task instead of expressing the entire task through the usual file-operation sequence. [XA-W002]

Coordinating an HTTP response across storage and networking#

Cheetah applies application knowledge across another boundary. An HTTP server receives a request, locates a document and sends it to a client. The XIO library and Cheetah implementation allow storage and TCP handling to be organized together around this task. Their optimizations concern the path from cached or stored document to transmitted response. [XA-W002]

Cheetah merges the file cache with the TCP retransmission pool. It transmits document data directly from cached pages, using precomputed checksums stored with the files. If a retransmission is required, the same cached data can supply it. Separate copies for file caching and retransmission become unnecessary. The arrangement joins knowledge of the stored object to the communication protocol’s requirements. [XA-W002]

Knowledge of the request also affects packet scheduling. Cheetah delays acknowledgment of a client’s request when it expects to include that acknowledgment with the response, reducing separate control packets. This matters particularly for small documents, where one packet is a substantial part of the

exchange. On disk, it groups files included by an HTML document near that document when possible, making related requests cheaper when the cache does not absorb most of the workload. [XA-W002]

The evaluation compares conventional OpenBSD servers, a base socket server on OpenBSD, that server using socket interfaces on Xok, and Cheetah’s specialized path. For documents of one kilobyte or less, Cheetah obtained approximately four times the throughput of the Xok socket-based implementation and eight times the best performance the authors achieved on OpenBSD. For larger documents, Cheetah delivered more than 29.3 megabytes per second with the CPU idle over 30 percent of the time, whereas the socket implementation reached 16.5 megabytes per second at full CPU utilization. The machines used 200 MHz Pentium Pro processors; the server’s available network bandwidth came from three 100 Mbit/s Ethernet connections. [XA-W002]

The external HTTP/TCP exchange remains recognizable while internal operations are coordinated differently. The paper reports that even its default socket and filesystem implementations benefited from changes such as packet merging and cached pointers to file blocks. Further specialization then used knowledge of the complete response. In this history, retaining a familiar interface and exposing another route for application-specific control were both productive choices. [XA-W002]

What the exokernel builders learned#

The authors’ later account distinguishes fast primitive operations from control over expensive work. Aegis had been heavily tuned for microbenchmarks; Xok had not. They nevertheless obtained strong application results by changing I/O and other substantial operations. They also describe a practical development advantage: a library can be edited, compiled, relinked and debugged without the repeated kernel reboot cycle. Another library operating system can remain available while the experimental one is developed. [XA-W002]

Designing a suitable protected interface still took repeated iterations. It had to expose enough control while preserving the invariants needed for sharing. Self-paging libraries also required careful treatment of circumstances in which the software responsible for obtaining memory itself needed memory. These were engineering problems encountered while constructing the systems, alongside the improvements their architecture enabled. [XA-W002]

The project’s distribution notes describe a system suitable for library-OS and application development, with restricted disk and Ethernet controller support, bugs and unimplemented features. They also distinguish source-history events and available snapshots. The release account presents the state of a developing system; the performance papers present particular implementations and experiments. [XA-W008]

Reusing a kernel by introducing an adaptation layer#

田崎創’s 2017 account of Linux Kernel Library begins with a reuse problem. Accessing a filesystem created under another operating system requires an implementation of its semantics. Reimplementing a large, evolving filesystem is substantial work; booting a complete guest operating system is another possible route. LKL makes existing Linux kernel functionality available as a library that a surrounding program can use. [XA-W005]

Its adaptation layer occupies the place normally used to accommodate a processor architecture. Instead of adapting Linux solely to a different CPU, it mediates between the kernel code and the surrounding execution environment. Time, scheduling and memory are supplied through that environment, and virtio supports transfers to external devices. This makes the same core functionality usable through several hosts. [XA-W005]

Applications can call the LKL system-call interface, use an interposition library that redirects calls, or follow a musl-based compilation route. The interfaces above and below the reused kernel make that kernel useful in a new setting. Here additional abstraction serves reuse: the design does not seek its benefit simply by removing intermediate components. [XA-W005]

The author examines the implementation with netperf against ordinary Linux 4.9.0, using two PCs connected through Intel X540-T2 10 Gbit/s Ethernet interfaces. Large TCP transfers exploit segmentation and checksum offload, limiting the reported throughput reduction to about ten percent. Smaller transfers lack the same batching advantage. The reported UDP deficit reaches 47 percent at a 1024-byte payload, while much larger payloads approach ordinary Linux performance. These measurements connect the reused functionality to the actual transfer sizes and processing path. [XA-W005]

Keeping familiar calls while selecting the machinery underneath#

Unikraft organizes a specialized system from selectable micro-libraries. Its 2021 account describes components with explicit dependencies and build configurations, so that the final image includes the functionality required for the application. Scheduling can be omitted for a suitable single-threaded or run-to-completion task. Locking primitives can similarly disappear when the configured execution circumstances do not require them. [XA-W003]

The memory-allocation design preserves a familiar external interface while opening choices underneath it. A POSIX-facing allocation interface supports existing application code. The internal ukalloc interface directs requests to an allocator backend, and a caller using that internal interface specifies which backend to use. Backends have their own memory regions and allocation functions. Boot code and application code can therefore use different allocators without requiring every ordinary allocation call to expose that choice. [XA-W003]

Application support uses native builds and compatibility components. A syscall shim connects libc’s required operations to implementations available in the image, allowing calls to become ordinary function calls. The paper reports 146 implemented system calls and additional work for glibc-specific compatibility. Its application evaluation uses manual ports of nginx and Redis, selected configurations and single-core virtual machines. Those workloads ran 70–170 percent faster than the Linux VM comparisons reported there; allocator choices and security-mitigation settings affected the differences. [XA-W003]

Startup measurements distinguish the guest from the virtual-machine monitor. A guest’s initialization can take far less time than the complete operation of launching it. The paper reports total startup of approximately three milliseconds with Solo5 and Firecracker, including their monitor overhead. Selecting and initializing fewer components contributes to the result. These are choices about the constructed system and its launch path as well as about application instructions. [XA-W003]

Lefeuvre and colleagues’ developer overview places this work within earlier attempts to make unikernels useful. They identify restricted application support, unfamiliar tooling, insufficient modularity and missing security mechanisms as obstacles. They also question the inference that a small image alone provides strong security. Their proposed development direction joins specialized execution to support for applications, actual protection mechanisms and familiar operational tools. [XA-W007]

Shortening a known path inside Linux#

Unikernel Linux takes a different starting point: retaining Linux and its ecosystem while allowing one application to be linked with the kernel. Raza and colleagues’ base model replaces system-call instructions with procedure calls but preserves much of the existing execution machinery. Application

and kernel code retain different stack and execution conventions. Ordinary user processes can run alongside the optimized application. [XA-W004]

The optimized application runs with supervisor privilege. Other processes are not protected from it in the manner that separate Xok applications are protected from one another; the UKL account uses external isolation where work requires that protection. Within this arrangement, developers can select further changes, including bypassing portions of entry and exit processing and choosing how stacks are handled. Preserving execution conventions supplies a working starting point from which more specific changes can be investigated. [XA-W004]

Redis supplies the developed application case. Profiling shows its read and write operations passing through generic dispatch before reaching TCP routines. Since the relevant Redis operations use TCP, a shortcut can invoke tcp_recvmsg and tcp_sendmsg directly. The authors report modifying about ten lines of Redis to use it. This changes the underlying path, rather than only the instruction used to enter that path. [XA-W004]

In the reported bare-metal experiment, the base model improved throughput by 1.6 percent over Linux. The bypass/return configuration improved it by twelve percent; adding the shortcut improved it by 26 percent. The 99th-percentile latency changed from 3.26 milliseconds for Linux to 2.54 milliseconds for the shortcut configuration. The comparison used matching kernel and library versions, with the specified security mitigations disabled on both systems. Its separate virtual-machine experiments produced different, smaller gains. [XA-W004]

The authors’ performance-counter analysis follows instructions, cycles, branches and caches. The shortcut configuration executes fewer instructions and branches and makes fewer cache accesses; the reduction in cycles is greater than the reduction in instructions. They interpret the changed path and improved cache behavior as important to the result. The experiment therefore develops the engineering beyond replacing a system-call instruction: it follows how application knowledge changes the work that remains in the execution path. [XA-W004]

Changing a working platform with its maintainers#

UKL’s implementation coordinates changes to Linux, glibc and application code. Configuration-specific changes keep the base kernel patch relatively small and allow normal configurations to remain available. The authors describe months of discussion with kernel developers at Red Hat and an October 2022 request for comments to the Linux kernel mailing list. Their comparison of patches records the files and subsystems affected, including the maintainers whose review and approval would be required. [XA-W004]

Richard Jones’s 2023 project account describes further work before another community submission: separating patches, preparing useful commit messages and checking Linux standards and tests. Demonstrating a useful configuration and obtaining its acceptance into a shared platform are separate parts of this history. The participating team could build and measure a coordinated optimization while still needing review of changes intended for wider incorporation. [XA-W006]

This account gives the organizational questions developed in S07 a particular engineering setting. Decisions about an experimental image, changes to an application and acceptance into a maintained common platform involve different participants and commitments. In Jones’s account, the subsequent work is to prepare the changes for review and demonstrate their usefulness with additional workloads and collaborators. [XA-W006]
