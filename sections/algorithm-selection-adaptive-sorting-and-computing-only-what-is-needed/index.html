Choosing a method for an instance#

Lars Kotthoff's 2012 survey organizes algorithm selection around problem instances, descriptive features, a set of candidate algorithms and a performance measure. Its account of the earlier Rice framework makes the selection problem explicit: map information about an instance to a method expected to perform well on it. The desired result might be a short running time, a high-quality solution within a budget, or success on a difficult search problem. An algorithm's favorable average over one collection of instances need not make it the best choice for every member. [TD-W024]

The survey distinguishes choosing one algorithm before execution from scheduling a portfolio and from responding to observations during execution. A static selector might use instance features measured in advance. A schedule can allocate time among solvers, while an online approach obtains further information as work proceeds. These arrangements offer different ways to use uneven performance. They also require decisions about which features to compute, how expensive those computations may be, and when to use a default instead. [TD-W024]

Feature computation is itself work that can be budgeted. A predictor that needs an expensive search to describe an instance may consume the time that its choice was supposed to save. Kotthoff discusses selection and feature costs as part of assessing the system, along with the chosen algorithm's performance. The engineering question is consequently concrete: what can be learned economically about this instance, and which decision can still be changed by learning it? The histories of numerical preparation and precision in S35 and S55 concern other ways in which the representation and conduct of a computation affect its performance. [TD-W024]

Different kinds of partial order#

Vladimir Estivill-Castro and Derick Wood's 1992 survey shows why “nearly sorted” needs a specified meaning. Straight insertion sort maintains an ordered prefix and inserts each new item by moving larger predecessors aside. Each such shift removes one inversion: a pair whose earlier item is greater than its later item. If there are I inversions among n items, the work is O(n + I). A sequence with only O(n) inversions can therefore be sorted in linear time by this method. The relevant quantity is the number of inverted pairs, rather than simply how many items look displaced. [TD-W025]

Consider two explanatory inputs. The sequence [2, 1, 4, 3, 6, 5, 8, 7] has four inversions and four adjacent descents. Straight insertion needs four shifts of larger predecessors. The sequence [5, 6, 7, 8, 1, 2, 3, 4] has only one adjacent descent, but sixteen inversions: every item in the first half exceeds every item in the second. It consists of two ascending runs, which a merge can combine with linear work. Generalizing the second construction to two equal sorted halves gives n2/4 inversions even though only two runs need merging. [TD-W025]

A linear scan can find adjacent descents and run boundaries. That does not make it a linear-time count of all inverted pairs. Different measures expose different opportunities: few inversions suit ordinary insertion, while a few long runs favor merging. The survey develops adaptive sorting through explicit measures of disorder and bounds relative to the number of inputs compatible with a given amount of disorder. It reports Mannila's formalization and examples of algorithms designed to meet such bounds. [TD-W025]

This analysis does not contradict the worst-case comparison bound for unrestricted sorting. If a comparison procedure must distinguish all n! orders of distinct keys, its decision tree needs enough

leaves to represent them, requiring Ω(n log n) comparisons in the worst case. A restricted class can contain fewer possibilities, and an adaptive algorithm can do less work on favorable inputs while retaining a larger worst case elsewhere. Sortedness is itself recognizable in linear time by checking neighbors. The useful distinction is between the task's worst case and the work justified by the particular order already present. [TD-W025, TD-W026]

Using the key representation#

MIT's 2011 linear-time sorting notes contrast comparison sorting with methods that inspect keys as data. Counting sort assumes integer keys in a range of size K. It allocates positions or buckets for those keys, scans the n records to count or distribute them, and visits the key range in order. The time is Θ(n + K); a record-carrying bucket implementation also uses Θ(n + K) space. If keys represent ages from zero through one hundred, K is small. If two keys are zero and a trillion, the same direct range allocation is unattractive despite the small number of records. [TD-W026]

Least-significant-digit radix sort instead represents a key by d digits in base b and performs a stable counting pass for each digit, from least to most significant. Stability preserves the order established by earlier passes among records sharing the present digit. For an explanatory example, sorting 21, 12, 11 by units gives 21, 11, 12, retaining the order of the two records ending in one; a stable tens pass then gives 11, 12, 21. The bound is Θ(d(n + b)). It becomes linear in n under suitable restrictions on d and b. A small key range, a bounded digit representation and a favorable probability distribution are different assumptions, each supporting different methods. [TD-W026]

Making radix sorting practical#

Peter McIlroy, Keith Bostic and M. Douglas McIlroy's 1993 engineering study treats string sorting as a problem of using the bytes already present in keys. A most-significant-byte distribution forms piles by the next byte and recursively sorts each unfinished pile. Strings sharing a prefix then advance together to the next position; a completed string need not continue through later characters. This avoids repeatedly rediscovering a long common prefix through whole-string comparisons. [TD-W027]

The bookkeeping matters. Clearing or scanning every possible byte pile can dominate when only a few piles are occupied, so the authors examine ways to track the occupied range or piles. Small piles can be finished by an insertion method rather than paying the full distribution overhead again. Their “American flag” method counts pile sizes, computes their destination ranges, and cycles misplaced string descriptors into the appropriate ranges in place. Once a descriptor is placed, the displaced descriptor supplies the next item to move. This yields an in-place distribution without requiring a separate full array of descriptors, although the permutation is not stable. [TD-W027]

Recursion order also affects storage: leaving the largest pile until last limits the stack needed for the remaining work. The article combines these details with tests on actual workloads and attention to the sorting interface. Its performance gains belong to those implementations and data. The enduring substance of the account is visible in the connected construction: use a key's next byte, group a shared prefix, avoid empty-pile work, move descriptors through counted ranges, and switch methods where a smaller routine is preferable. [TD-W027]

Sampling and equal-key blocks#

Jon Bentley and M. Douglas McIlroy's 1993 account of a library sort began with inputs that defeated existing implementations. Organ-pipe patterns and arrays containing only zeros and ones exposed quadratic behavior. The replacement was developed for a general interface in which a caller supplies the comparison operation and records may be expensive to exchange. Comparisons, swaps and partition

bookkeeping therefore had different costs from those in an abstract count of unit-time operations. [TD-W028]

Pivot sampling varied with size: a middle element for small inputs, a median of three for larger ones, and a pseudomedian assembled from nine samples for still larger ones. The authors chose thresholds empirically rather than presenting a single sampling rule as costless at every size. Their partitioning also gathered equal keys so that, after rearrangement, the middle block contained items equal to the pivot. Only the less-than and greater-than blocks required recursive sorting. With an all-equal input, one partitioning scan could finish the problem. [TD-W028]

For an explanatory zero/one input, choosing zero as pivot collects the zeros into the equal block and leaves only the ones on the greater side. Sorting need not repeatedly partition the zeros as if they still had unknown relative ranks. The authors' split-end partitioning implements this treatment of equals while supporting the general library interface. The paper supplies an engineering account of robustness across troublesome inputs; it should not be conflated with later introspective sorting methods that add a worst-case fallback. [TD-W028]

Choosing which runs to merge#

Natural mergesort discovers ordered runs, but it still must decide which adjacent runs to combine and in what order. A merge of runs of lengths a and b costs in proportion to a + b. Repeatedly merging a long run with each small arrival can scan its contents many times. A suitable merge tree limits how often an item travels through successive merges while preserving the adjacency needed for stable sorting. This is the problem addressed by J. Ian Munro and Sebastian Wild's 2018 peeksort and powersort algorithms. [TD-W029]

Peeksort finds the run around the middle of an interval and recursively organizes work around the resulting boundaries. Powersort processes runs from left to right and assigns a power to the boundary between neighboring runs. The power records the first binary subdivision depth that separates their normalized midpoints. It represents where the boundary belongs in a nearly balanced tree without requiring the entire run sequence in advance. When a new boundary has a shallower power than a pending one, the deeper work is merged first. A stack retains the unfinished adjacent pieces. [TD-W029]

For run lengths L1 through Lr totaling n, the authors use the entropy H = Σ(Li/n) log2(n/Li). It reflects the distribution of run lengths: one long run and several tiny ones need not require the merge work of many equally sized runs. Their powersort analysis bounds total merge cost M by nH + 2n. The additive linear term makes the result nearly optimal in this cost model. The measured runtime also depends on the implementation of a merge, memory traffic and comparisons. [TD-W029]

Vincent Jugé's 2020 account of adaptive ShiversSort develops another economical policy. It uses levels derived from the integer parts of the base-two logarithms of run lengths and examines only the top three runs on its stack when deciding the next merge. Run-size comparisons determine whether an older pair should be combined before the newest run is allowed to remain pending. This small local view is used to control the larger merge structure. The paper separates the merge policy from preparation of short runs and from optimizations inside a merge. [TD-W030]

Number the pending runs from the stack's top, so R1 is newest, and let each level be the floor of log2 of its length. If either of the top two levels is at least the third, the policy merges R2 with R3. Otherwise, if the top level is at least the second, it merges R1 with R2; otherwise it admits another run. At the end it merges the remaining stack. For an explanatory stack with lengths 8, 4, 4 from bottom to top, the levels are 3, 2, 2. The two top runs merge to length eight, after which the two eights merge. The older eight is not scanned once for each arriving four. [TD-W030]

Jugé states an nH + O(n) merge-cost bound for the adaptive policy and compares it with earlier guarantees. A better coefficient in an entropy bound concerns accumulated merge work, not an identical percentage reduction in execution time on every machine or input. The account shows how a compact rule operating on a few stack entries can be the subject of a substantial global guarantee. It also preserves a distinction between the historically described TimSort merge policies and later implementations adopting powersort. [TD-W030]

Adaptation during the work#

The sorting design notes shipped with CPython 3.14.0, released in October 2025, connect run discovery with the work of sorting itself. The implementation detects natural runs, normalizes descending runs, extends short runs with stable binary insertion, and uses powersort to organize their merges. Its treatment of equal-key subruns allows normalization while preserving stability. These are details of this frozen release, which incorporates developments after the original introduction of TimSort. [TD-W031]

For example, [3, 2, 1, 3, 4, 5, 0] begins with a descending stretch. Reversing its first three items produces [1, 2, 3], after which the scan can extend the ordered run across the following 3, 4, 5. Recognizing order and acting on it are interleaved. There need not be a separate, completed diagnosis of the whole input before sorting begins. If a run is too short for efficient merging, binary insertion brings it to the desired working length. [TD-W031]

During a merge, galloping responds to a sustained winning streak by one run. Exponential search followed by binary search finds a block that can be copied together rather than comparing each item against the other run's next item. The threshold adapts so that useful streaks encourage further galloping and unsuccessful attempts discourage it. The implementation therefore uses information at several scales: runs in the input, their lengths and merge positions, and temporary dominance during a particular merge. [TD-W031]

A rank without a full order#

Manuel Blum, Robert Floyd, Vaughan Pratt, Ronald Rivest and Robert Tarjan's 1973 selection paper proved that the item of a specified rank can be found with a worst-case linear number of comparisons. Their PICK construction sorts fixed-size columns, selects representatives, recursively finds a representative of controlled rank, and uses it to partition the original candidates. The representative is chosen so that a guaranteed fraction can be discarded. If the sought rank lies above the discarded lower part, its rank is adjusted within the remaining part; if below, the upper part becomes irrelevant. [TD-W032]

The original construction develops its guarantee through column sizes and representative positions, including a basic analysis with columns of twenty-one. Its result is about finding a rank, not arranging all items in order or necessarily supplying the fastest practical routine for a tiny requested subset. Once a cutoff rank is known, the relevant side of a partition can be retained without sorting the other side. Ordering the retained items is a further task whose size may be much smaller than n. [TD-W032]

Keeping a small extreme subset#

CPython 3.14's heapq implementation gives a practical streaming alternative for a small requested k. To retain the largest k items, a min-heap of k candidates exposes the smallest retained item at its root. Each new item is compared with that boundary. If it cannot enter the retained set, it is discarded; if it can, it replaces the root and the heap is repaired. After the scan, only k candidates remain. The worst-case work is O(n log k), with O(k) retained storage, followed by O(k log k) if the retained set is sorted for presentation. For a fixed ten candidates, the scan is linear in n. [TD-W031]

The release's nlargest and nsmallest functions include useful boundary cases: a request for one uses an extremum operation, and a request at least as large as a known input size can use a full sort. The functions return their retained results in order. Their heap entries also carry an order field, preserving a defined treatment of equal keys. A custom routine that only needs the set can leave its heap unordered; it should not assume that a library function returning ordered results omitted the final sort. [TD-W031]

Local top-k results also admit a simple merge. Under a consistent total ordering, an item excluded from a partition's top k already has at least k items ahead of it in that partition, so it cannot enter the global top k. The global answer is therefore contained in the union of the local answers; another top-k selection over that union suffices. Equal keys require a shared tie rule if exact membership matters. This is a direct consequence of the retained-set rule, illustrated by disjoint candidate partitions, rather than a separate empirical performance claim. Scanning a filesystem can involve additional work to compute directory totals or identify shared files; selecting the largest measured candidates is the part explained by this algorithm. [TD-W031]
