When local transactions compose safely#

Peter Bailis and colleagues ask when database transactions can execute without blocking coordination while preserving stated application invariants. Their framework makes the answer depend on the combination of an invariant, a transaction set, and a merge operation. The result concerns a declared database model. [W005, §§3–4]

The model represents a database state through versions of data items. A transaction operates on a logical replica, a partial view of versions, and changes to committed state are subsequently shared through merge. A logical replica is not necessarily a separate physical server. In the initial model, merge is set union: the resulting state includes the versions present on either side. The authors assume merge is associative, commutative, and idempotent for their discussion. Those algebraic properties describe how merges combine; they do not determine what application states are acceptable. [W005, §3]

Four requirements for coordination avoidance#

An invariant is a predicate that says whether a state is acceptable. The initial state must satisfy it. Global validity requires replica states to remain valid, including states reached by merging independently produced changes. Checking a transaction's immediate local result is therefore only part of what has to be established. [W005, §3, definitions 1 and 4]

Transactional availability is deliberately nontrivial. Under the stated access conditions, a transaction eventually commits except when its own abort operation or a violation of a declared invariant over its replica justifies aborting. Always refusing transactions is not an available solution in this definition. Convergence also rules out permanently isolated valid histories as a substitute for sharing state: without new writes and indefinite communication delay, servers eventually agree on versions of items they both store. [W005, §3, definitions 2–3]

Coordination-freedom concerns the progress of concurrently executing transactions. A transaction's progress depends on the versions it reads, rather than blocking synchronization with work performed for another transaction. This does not mean there is no communication. The model explicitly retains subsequent propagation and merge; an implementation may also communicate to provide a chosen durability level. Removing synchronous coordination between concurrent decisions is a more specific claim than eliminating every kind of network work. [W005, §3, definition 5 and discussion]

Reachability and the common ancestor#

The key property, invariant confluence, is defined over reachable states. A state is reachable in the relevant sense when transactions and merges can produce it through a history whose intermediate states satisfy the invariant. The criterion considers two such states with a common ancestor and asks whether their merge is also valid. Both reachability and common ancestry matter. The definition does not require arbitrary states that happen individually to be valid to merge safely, even when the permitted transactions could never have produced their divergent histories. [W005, §4.1, definition 6]

The source states a necessary-and-sufficient result: within its model, global invariant validity can coexist with coordination-freedom, transactional availability, and convergence exactly when the transaction set is invariant-confluent with respect to the invariant. The paper provides a proof sketch and directs the reader to a technical report for the full proof. [W005, §4.2, theorem 1]

Explanatory illustration: a property that survives union#

The following small example illustrates the paper's model and distinction. It is an explanatory construction for this monograph. Suppose the state is a set of records, and the only permitted transactions add records with nonnegative ages. Let the invariant require every stored age to be nonnegative. Start from the empty valid state. One history adds Alice, aged 30; another adds Bob, aged 40. Each result is valid, and their union is valid because each record in the union came from a side that met the same requirement. [W005, §§3–5, model and attribute constraints]

The reasoning extends over the specified add-only transaction set: none of its operations introduces a negative-age record, and taking unions does not introduce a record absent from both inputs. This explains why the property in this example is preserved through the permitted divergent histories and merge. It does not say anything yet about unique identifiers, correct billing, or other requirements that were not included in the invariant.

Change the invariant and the answer changes#

Now give the records identifiers, retaining set union as merge. Let the application invariant require that no two different people share an identifier. Two histories diverge from the same empty ancestor. On one replica, a transaction sees identifier 7 unused and inserts Alice with identifier 7. On the other, a transaction sees it unused and inserts Bob with identifier 7. Each local state satisfies uniqueness. Their merged state contains two different records with the same identifier and violates it. The local commit checks have not made the independent decisions composable. [W005, §§3–5, uniqueness discussion; explanatory illustration]

Idempotence does not repair this outcome. Unioning the already merged set with itself changes nothing. Alice's record and Bob's record are distinct elements; the duplicated application identifier does not make them the same version for set union. A stable, repeatable merge can therefore preserve an unacceptable result. The example shows why an algebraic merge property and an application invariant must not be substituted for each other.

Under the theorem's combination of obligations, the non-confluent pair prevents the unrestricted coordination-free conclusion for these operations and this invariant. One cannot save all the obligations simply by refusing to merge forever or by aborting every otherwise locally valid transaction. A different allocation operation, invariant, or representation would pose a different question and needs its own analysis. The paper's distinction between choosing a specific identifier and choosing some identifier is important for precisely this reason: uniqueness is not an unconditional verdict that every conceivable identifier-allocation design requires the same coordination. [W005, §§4.1–5]

Correctness still depends on what was specified#

The authors explicitly limit the framework to the invariants and operations supplied. If those requirements are incomplete or wrong, satisfying them need not satisfy the application's actual purposes. Specifying the requirements is itself substantive work. The framework can identify a possibility or an impossibility under its assumptions; it does not select every implementation, determine the relevance of every business rule, or demonstrate a net lifetime saving. [W005, §4.3]

Whether the local decisions compose safely depends on the allowed histories and the invariant under the chosen merge. The worked example exposes the temptation to infer application validity from idempotence alone. The answer depends on the specified database model and requirement.

What the coordination comparison actually compares#

Bailis and colleagues motivate their criterion by distinguishing serializability from application correctness. If each transaction is correct in isolation, an execution equivalent to a serial order supplies a powerful general guarantee. But not every interaction that conflicts at the read/write level compromises the application's selected invariant. Their proposal asks which combinations actually need synchronous coordination, rather than paying that cost for every general-purpose conflict. The distinction raises the specification from low-level interference to the application property that must remain true. [W005, §2]

Their measurements illustrate why that distinction can matter. An eight-server prototype comparison contrasts an optimized two-phase-locking implementation with execution without coordination. The latter avoids the locking bottleneck for its specified operations; distributed coordinated transactions suffer a much larger throughput drop as their scope expands. These are particular implementation and workload comparisons, supplemented by network-delay calculations using earlier trace studies. The paper explicitly notes that rare coordinating operations need not be a bottleneck and that disjoint read/write sets can allow a serializable database to perform similarly. The favorable case is therefore informative without establishing that removing coordination always improves the application's overall performance. [W005, §2, figs. 1–2]

The theorem and these measurements do different work. The criterion characterizes a possibility under the declared semantics; the benchmark measures particular costs under particular execution arrangements. Neither permits a correctness requirement to be silently discarded because avoiding it runs faster. Conversely, using a stronger general guarantee than the application needs can impose work that a more specific analysis could avoid.

Changing identifier allocation changes the problem#

The article's uniqueness discussion distinguishes “give this record this particular identifier” from “give this record some unique identifier.” In the latter case, replicas with known identities can allocate from disjoint portions of a namespace. Each then uses a space other replicas do not use; merging locally allocated identifiers does not introduce the collision caused by two replicas freely choosing the same value. The arrangement changes the allowed allocation operation and relies on membership information. The unrestricted-insertion counterexample above consequently does not refute this different design. [W005, §5.1]

This is a concrete example of prior structure changing a recurring interaction. The separated namespaces embody a constraint on which local choice can occur. Their suitability still depends on the actual identifier requirements and reliable handling of membership; a design requiring one particular shared identifier poses another task. The paper does not establish that choosing any identifier is an acceptable substitute in every application. Its result is strongest when the changed semantics remain explicit.

Referential integrity depends on the allowed updates#

For a foreign-key relationship, an inserted record requires a corresponding referenced record. In the article's non-destructive merge account, if every locally valid inserted reference has its target, union cannot make that target disappear. That argument explains a positive result for the specified insertions. Arbitrary deletion changes the situation: one history can add an employee to a department while another deletes the department. Each local view can meet its immediate requirements, yet their combined effect can leave a dangling reference. The condition is not simply “foreign keys are safe” or “foreign keys require coordination.” It depends on what updates and merge semantics are allowed. [W005, §5.1]

The source also considers cascading deletion and suitable propagation of related effects as different operations. Their treatment depends on the modeled semantics, not merely on attaching the word cascade to an implementation. It preserves the paper's reason for distinguishing the cases: validity can concern the visibility and persistence of related records as well as the immediate value in one field. Coordination requirements cannot be read from the invariant's name alone. [W005, §5.1]

Borrego and colleagues: a losing operation can become ineffective#

Dina Borrego, Nuno Preguiça, Elisa Gonzalez Boix and Carla Ferreira's 2025 No-Op approach maintains convergence and invariants through explicit conflict-resolution policies. In their music-data example, concurrently removing an artist and adding an album referring to that artist can threaten referential integrity. An update-wins policy can render the artist removal ineffective; a remove-wins policy can instead suppress the album addition. Both arrangements make a choice about which effect survives. They do not preserve both unrestricted effects while somehow making the conflict disappear. [W027, §§2–2.1]

The mechanism records operation calls and their causal dependencies in an execution graph. Concurrent calls remain unordered by causal edges. A winning call issues a block against an incompatible concurrent call, which is marked as a No-Op. When the other replica receives the relevant call, it can make the same determination. Replicas can therefore initially differ and subsequently agree after the required information is delivered. In the paper's update-wins trace, an artist removal that looked effective locally is later recognized as a No-Op. Immediate local appearance and eventual effective state must be distinguished. [W027, §2.1]

Their correctness argument assumes that every replica receives all updates, updates arrive in causal order, and a resolution policy exists for every conflicting pair. The claimed safe serializations and convergence retain those prerequisites. The workflow also retains programmers' responsibility for identifying conflicts and selecting policies. Verification of invariant preservation does not check that a chosen priority matches the programmer's intended meaning. A user-priority rule, for example, makes whose operation wins an explicit part of the arrangement. This remains a substantive semantic decision even when a formal check succeeds. [W027, §§2.2, 3.1]

The account is relevant alongside invariant confluence because it makes a changed obligation visible. Suppressing a losing effect is a particular concurrency semantics, not a counterexample to a theorem holding fixed the original transactions and its availability/validity obligations. Comparing the sources requires retaining what each permits to be discarded or made ineffective.

Bailis's dissertation: specification and mixed execution#

In the conclusion of his 2015 doctoral dissertation, Bailis describes four limitations of coordination avoidance. The invariant-confluence analysis has effectively assumed that program text and constraints are known in advance. A restricted safe language could permit some dynamic programming, but its usefulness still depends on admissible logic and complexity. This is an explicit condition on what has to be available before the runtime advantage can be established. [W057, ch. 8, printed pp. 185–186]

The same passage emphasizes complete correctness specifications. An invariant absent from the specification is treated as irrelevant to correctness. The programmer therefore bears a burden that does not disappear when the selected invariant is formally preserved. Bailis also describes the analysis and construction of algorithms as primarily manual, using proofs, rudimentary static analysis and design principles. [W057, printed p. 186]

Finally, the passage identifies mixed execution as an unresolved practical issue. Always coordinating whenever the criterion does not hold can waste opportunities; realizing the benefit may require combining coordinated and coordination-free semantics within one runtime. [W057, §8.2]

Sato: files and prior transactions supply state#

Ryo Sato's 1992 paper offers a state-space representation of business transaction systems, drawing its general system definitions from Mesarovic and Takahara. The selected opening pages treat operations such as orders, purchasing and bookkeeping as discrete events that can occur in parallel. Files retain accumulated past transactions, while internally set events also contribute to the state governing subsequent response. The proposed model therefore does not identify a business system only with a stream of current requests: its stored history changes how an incoming event can be handled. [SG-W035, printed pp. 184–187]

Sato's data-model definitions distinguish file types, attributes, keys and actual file contents, then formulate integrity conditions, including references between files. They supply a language for saying what information and constraints a transaction system contains. [SG-W035, definitions and prose, printed pp. 185–188]
